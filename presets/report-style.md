# 汇报风格（主管转达给你时必读）

出厂预置文档，播种到用户目录后归你所有——可以改、可以删（删了主管就按内置的默认规则汇报）。

主管每次把员工的产出转达给你之前，会完整读到本文件，据此决定「这一条该怎么写给你看」。
所以**这里写的是你想看什么**：想加「一定要带耗时」「commit 给全长 sha」「先说结论再说别的」，
直接改这份文件即可，不用改代码。

> 这份规则只影响**聊天里发给你的那段文字**。员工交卷的结构化字段（结论 / 交付物 / 验证 /
> 风险 / 关键决策）照旧完整落进任务档案、工作台与复盘输入——看板里随时能展开看全量，
> 精简的是视图，不是数据。

## 通用规则

不按任务类型套模板（任务类型太多，模板永远不够用），只守下面这几条：

1. **开头第一句就是我最关心的那件事的结论。**
   修 bug → 根因是什么 + 修没修好；查数据 → 那个数字；配置/部署类 → 生效没生效；
   调研 → 结论与建议。别拿背景、复述诉求或「我先……然后……」开头。

2. **信息按「我接下来要不要做点什么」排序**，不按员工的干活顺序排。
   需要我决策、需要我知道的风险，排在细节前面。

3. **只写我不知道的。** 我自己提的诉求不要复述；同一个事实只出现一次。

4. **这些一律不写**（属于内部编排，我不为此付出注意力）：
   - 怎么拆步骤、为什么这么拆、派了谁、编了几步
   - 调用了什么工具、读了哪些文件、跑了什么命令来自查
   - 重试几次、评审几轮、会话怎么续、为什么换人
   - 「我亲自复核了」这类表态——复核是本职，不是成果

5. **可核验的坐标必须原样保留，一个字符都不许改。**
   文件路径、行号、commit、分支、URL、关键数字。这是我复核的抓手，也是最不该被总结掉的东西。
   拿不准要不要留的细节，先留坐标、砍叙述。

6. **风险只留会改变我判断、或需要我动手的那些。**
   「同类缺陷还有一处没修」要写；「因为没装依赖所以没跑构建」只在它确实影响结论可信度时写一句，
   不要列成清单。没做验证就如实说没做，别用一堆过程掩盖。

7. **长度自适应。** 一句话能说完就一句话，别为了凑格式硬分段；复杂任务才分段。
   宁可短到显得简陋，也别长到需要我自己找重点。

8. **不评价、不脑补、不邀功。** 只能重组员工产出里**已经明确存在**的事实；
   报告里没有的东西不许出现，包括「应该没问题」这种推测。

## 反例（真实发生过，别再这样写）

一个 bug 修复任务，用户要的是「根因 + 改了什么」，实际收到的是五大段：结论里塞了根因也塞了
commit，交付物又把同一个 commit、同一个文件、同样的 +9/-1 重复一遍，验证列了四条
「我 Read 了诊断报告、我 Bash 了 git diff、我 Bash 了 git log」，关键决策列了四条
「为什么拆两步、为什么不设确认关卡、为什么禁装依赖、为什么复用仓库副本」。

用户真正需要的三行藏在里面：根因（`Tag.StateTag` 丢了 `extraText`/`url`）、
改动（哪个文件哪一行 + commit + 分支）、还有一处同类缺陷没修。
