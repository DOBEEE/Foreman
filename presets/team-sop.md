# 编队 SOP 手册（组长必读）

出厂预置文档，播种到用户目录后归你所有——可以改、可以删（删了组长就只靠自己的判断编队）。
组长每次编队前会完整读到本手册；复盘沉淀的新经验会另外注入「岗位经验库」，两者冲突时以经验库里更新的实践为准。

## 〇、触发索引（主管读这一段，决定「要不要编队」）

下面这个代码块是**主管与组长共用的单一事实源**：主管派工时只读它，据此判断一个任务
该交给组长编队、还是直接派给某个单人；组长拿到的是整本手册。改这里就等于改路由。

> ⚠️ 删掉这个代码块（或整份手册）的后果：主管不再主动编队，所有任务都按单人派工。

    {
      "template": "模板 A：实现 + 代码评审",

      "steps": "coder 实现 → code-review 评审"
    },
    {
      "template": "模板 B：诊断 → 修复 → 验证",

      "steps": "alert-diagnosis 定位 → coder 修复（配评审）→ 验证"
    },
    {
      "template": "模板 C：调研 → 方案 → 评审",
      "when": "技术选型、架构方案、迁移评估等要先摸清事实再出方案的活",
      "steps": "assistant 调研 → 出方案 → code-review 评审"
    }
  ],
  "exceptions": [
    "琐碎单点改动：改文案、改颜色、改常量、单行配置、加个日志——直接派 coder，编队的开销大过收益",
    "纯提问 / 查资料 / 读代码答疑，不产出改动 → 派 assistant",
    "用户明确只要其中一步（「只帮我看看代码质量」→ code-review；「只定位别改」→ alert-diagnosis）"
  ]

## 一、常用编队模板（优先套用，套不上再自由设计）

### 模板 A：实现 + 代码评审（最常用）

适用：写代码、改功能、修 bug，且要求质量把关。

| 步骤 | 执行者 | 要点 |
|---|---|---|
| `implement` | coder | brief 写清需求背景、涉及仓库/目录、期望产出、边界；配 `reviewer: code-review` |
| | | `accept`：「无严重级问题；建议级问题不阻塞。改动范围不超出需求」 |
| | | `maxRetries`: 2 |

收尾复核要点：产物文件是否真的存在、构建/类型检查是否真过。

### 模板 B：诊断 → 修复 → 验证

适用：线上告警、报错、疑难 bug。

| 步骤 | 执行者 | 要点 |
|---|---|---|
| `diagnose` | alert-diagnosis | brief 带上用户给的全部日志/堆栈/仓库地址 |
| `fix` | coder | brief 用 `{{step:diagnose}}` 注入根因结论；配 `reviewer: code-review`，accept 要求「修复覆盖根因、无副作用」 |
| `verify` | coder 或 temp | 跑构建/测试/复现步骤，输出验证结论 |

注意：诊断岗只定位不改代码，别让它顺手修。

### 模板 C：调研 → 方案 → 评审

适用：技术选型、架构方案、迁移评估。

| 步骤 | 执行者 | 要点 |
|---|---|---|
| `research` | assistant（或 temp 检索员并行分工） | 收集事实，要求标注来源 |
| `design` | coder / assistant | 基于 `{{step:research}}` 出方案，含取舍与风险 |
| `review` | code-review | accept：「方案可落地、风险已识别、取舍有依据」 |

## 二、选人原则

1. **看 routeHint 而不是看名字**：每步执行者必须职责对口；拿不准就选职责描述最贴近的那个。
2. **看忙闲**：花名册标了 `busy` 的员工手上有活。有空闲的对口员工优先用空闲的；只有忙的那位对口就照常派（系统会串行），并预期更慢。
3. **评审人必须与执行者不同**（自审无效），且必须是正式员工。
4. **步骤数 3~5 个为宜**，一步一件事。超过 8 步说明拆得太碎，合并。

## 三、accept（验收标准）怎么写才有用

- ✅ 可判定：「构建通过、无 TypeScript 报错、无严重级评审问题」
- ✅ 划范围：「只改 A 模块，不动公共配置」
- ❌ 空话：「代码质量好」「符合规范」——评审人无法据此判定，等于没写

写 accept 时想一句：「评审人拿着这句话，能明确说出 pass/fail 吗？」

## 四、临时工（temp）使用边界

临时工是你在 plan 里现场定义的一次性执行者：`employee: "temp"` + `temp: { role, prompt?, tools? }`。
**默认可读写、可执行命令**（只读集 + Write/Edit/Bash，不含 Task），用完即弃，
**没有经验库、不参与复盘、不能当评审人**。需要更严格就在 `temp.tools` 里显式收窄。

- ✅ 该用：无人负责的辅助活——批量检索汇总、提取接口签名清单、格式转换、多文件摘要、
  整理成表格、跑一段脚本/构建、批量改文案这类机械性改动。
- ❌ 不该用：任何有对口员工的活（有 coder 就别让临时工写代码）；质量把关；需要经验积累的判断题。
- 判断口诀：**这活干完，经验值得留下来吗？** 值得 → 交员工（他有经验库）；不值得 → 临时工。
- 反复需要同一种临时工 → 说明该正式招人了，在汇报的「风险与遗留」里建议用户找 hr 招一个。

## 五、常见坑

1. **brief 写太薄**：执行者只看得到你的 brief 和 `{{step:<id>}}` 注入的上游结论，看不到用户原话之外的任何上下文。别假设他"知道"。
2. **忘了串联**：下游步骤要用上游结论就必须写 `{{step:<上游id>}}`，不写就等于没给。
3. **该问不问**：目标或验收标准有歧义时硬编 plan，结果全队白干一轮。宁可先花一次 mcp__ask__ask_user 提问。
4. **收尾只抄结论**：收尾必须自己动手抽查产物（Read/Bash），执行者说"已完成"不等于真完成。
5. **粉饰未通过的步骤**：评审始终没过的步骤必须写进 `risks`，如实说明。
